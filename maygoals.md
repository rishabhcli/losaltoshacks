# May Goals: The Impossible MarketPulse Mandate

This document is intentionally too large for any single engineer, team, company, or AI agent to finish. It is not a normal roadmap. It is a gravity well for goal-mode execution: a maximal, unreasonable, world-scale ambition designed to keep pushing this application toward usefulness, autonomy, evidence, and real-world impact.

The mission is to transform MarketPulse from an AI-assisted market research application into an autonomous economy engine: a system that continuously maps unmet human and business demand, invents solutions, launches real products, operates them, learns from the market, and recursively improves its own ability to create economic value.

If an AI agent is set into goal mode with this file, it must not treat these goals as inspirational prose. It must convert the grand impossible mandate into concrete shipped slices, verified behavior, tests, runtime proof, and visible product improvements. It should always pick the highest-leverage unfinished slice it can actually execute, complete it, verify it, document what changed, and then continue.

## Prime Directive

Build the best possible version of this application.

Not a demo. Not a pitch deck. Not a dashboard that merely describes opportunities. Build a living system that can discover, validate, create, launch, measure, operate, and improve real products and ventures.

The app must eventually behave like a tireless AI-native institution:

- It researches the world.
- It detects unmet demand.
- It models markets.
- It generates business theses.
- It builds working software.
- It deploys products.
- It runs experiments.
- It talks to users.
- It measures traction.
- It kills weak ideas.
- It scales strong ones.
- It remembers every lesson.
- It improves its own process.
- It becomes better at creating companies every time it fails.

This is impossible at full scale. That is the point. The agent must still make it less impossible every time it works.

## Goal-Mode Operating Contract

An agent working from this file must obey the following loop:

1. Inspect the current repository and runtime reality before acting.
2. Identify the largest unfinished capability that can be advanced now.
3. Prefer shipped product behavior over planning documents.
4. Prefer real data, real tests, real browser proof, and real user-visible surfaces.
5. Make the smallest coherent slice that moves the impossible mandate forward.
6. Verify the slice with type checks, tests, builds, browser checks, API checks, or equivalent runtime evidence.
7. Record what was improved and what remains impossible.
8. Continue to the next highest-leverage slice.

The agent must not stop merely because the full mission is impossible. It may stop only when the current execution environment, missing credentials, unavailable services, or explicit user instruction blocks meaningful progress. Even then, it must leave the app in a better state than it found it whenever possible.

## North-Star Product

The final imagined system is an autonomous economy engine.

A user should be able to ask:

> Find an overlooked high-value business opportunity, prove whether anyone wants it, build the first product, launch it, get initial demand signals, and tell me whether to continue.

The system should eventually return something like:

> I found a repeated workflow pain among regional logistics operators. I evaluated 138 companies, mapped competitors, interviewed proxy sources, generated 23 product concepts, simulated the unit economics, built 3 MVP variants, deployed 2 landing pages and 1 working app, contacted 400 buyers, booked 11 demos, got 2 paid pilots, killed the weaker variants, and produced a surviving company workspace with source code, metrics, CRM records, pricing evidence, risk notes, and the next 10 actions.

That is the standard. Anything less is merely a stepping stone.

## Acceptance Gates for Any Slice

A slice counts only if it improves at least one of these:

- The app can discover better opportunities.
- The app can reason with stronger evidence.
- The app can produce more executable artifacts.
- The app can launch or prepare real experiments.
- The app can measure reality more accurately.
- The app can help the user make a better kill/continue decision.
- The app is more reliable, testable, observable, or recoverable.
- The user can see, inspect, trust, or operate more of the system.

Every completed slice should include as many of these proofs as possible:

- Passing type checks.
- Passing tests.
- Passing build.
- Browser verification.
- API health check.
- Data migration proof.
- Screenshot or visual inspection.
- Audit trail.
- Changelog.
- Clear next task.
